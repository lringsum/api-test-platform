# 接口自动化工作流规则

这份文档沉淀的是本项目里“从文档到用例到执行”的默认工作方式。

它主要来自旧项目会话里反复出现的真实操作链，而不是泛泛的测试理论。

## 1. 适用场景

适合以下输入：

- ShowDoc / YYDocs 接口链接
- 已复制出来的接口文档文本
- 指定项目、模块、环境后，让平台自动生成一条正向用例

历史高频场景：

- `天机` 项目
- `素材库`、`素材文件夹`、`素材工单`

## 2. 默认目标

如果用户没有特别说明，默认目标是：

1. 先生成一条正向接口测试用例
2. 保存到已有项目和模块
3. 选择环境执行一次
4. 校验请求、响应、断言、提取值是否正常
5. 再决定要不要补异常/边界用例

不要一上来就批量造很多异常用例，除非用户明确要求。

## 3. 默认录入规范

### 3.1 项目和模块必须明确

在保存用例前，应当优先明确：

- `project_id`
- `module_id`
- 目标环境

如果没有明确指定，优先使用当前上下文项目，而不是随便落到别的项目。

### 3.2 命名优先保持可读

历史里用户多次强调“文档名 - 用例名”这一类命名可读性。

推荐规则：

- 用例名优先使用：`接口名称-场景名`
- 第一条默认正向用例可用：
  - `接口名称-正常请求`
  - `接口名称-正向验证`

不要默认用太抽象的英文名或编号名。

### 3.3 先正向，后异常

默认顺序：

1. 正向
2. 参数缺失
3. 参数非法
4. 权限不足
5. 边界值
6. 组合异常

这样最符合平台实际使用节奏。

## 4. 用例结构规则

当前平台里一条标准 API 用例，至少要能落到这些结构：

- `method`
- `url`
- `headers`
- `params`
- `body`
- `extract`
- `assertions`
- `pre_script`

从当前代码看，入口主要在：

- [api_v1.py](D:/work/test_web/api-test-platform/app/routes/api_v1.py)
- [testcase_service.py](D:/work/test_web/api-test-platform/app/services/testcase_service.py)

### 4.1 请求路径规则

- `url` 必须是以 `/` 开头的相对路径
- `base_url` 来自环境
- 不要把完整域名硬编码进用例

### 4.2 认证规则

如果接口依赖登录态或 token：

- 优先从环境变量或前置登录结果里取 token
- 不要把真实 token 直接硬编码进用例正文

### 4.3 提取规则

只提对后续执行真的有价值的字段：

- token
- user_id
- resource_id
- workflow_id

不要为了“看起来完整”而提一堆无用字段。

### 4.4 断言规则

第一条正向用例的断言应优先覆盖：

- HTTP 状态码
- 业务码
- 核心成功标记
- 必要字段存在

不要只断言 `200` 就结束。

## 5. 保存规则

接口文档需人工整理为平台用例 JSON，保存前至少做一轮结构校验。当前版本不提供 AI 解析、生成或 Prompt 模板业务入口。

推荐保存前检查：

- method 是否存在
- url 是否合法
- headers / params / body 是否是对象结构
- assertions 是否至少有 1 条
- extract 是否只包含必要键

## 6. 执行规则

执行一条用例时，默认链路是：

1. 加载项目和环境
2. 拼运行时变量
3. 构造请求
4. 发请求
5. 做断言
6. 提取变量
7. 记录执行详情
8. 更新执行汇总

关键文件：

- [execution_service.py](D:/work/test_web/api-test-platform/app/services/execution_service.py)

### 6.1 执行不是无状态

平台会把提取值写回运行时变量，必要时回写环境变量。

这意味着：

- 一条登录用例可能影响下一条业务用例
- 复跑前要关注环境里是否残留旧变量

### 6.2 环境必须匹配项目

执行前要确认：

- 环境属于当前项目
- 环境处于激活状态
- 环境存在 `base_url`

## 7. ShowDoc / YYDocs 接口转平台用例的默认步骤

推荐步骤：

1. 读取文档标题、路径、方法、参数、响应样例
2. 识别所属项目、模块、环境
3. 先生成正向用例
4. 保存到平台
5. 执行一次
6. 根据响应补断言和提取
7. 再决定是否补异常用例

如果文档信息不全，优先补齐最关键的：

- 方法
- 路径
- 主要参数
- 成功响应判断

## 8. 常见风险

### 8.1 文档看着对，但路径不能直接跑

常见问题：

- 文档是完整域名，但平台要求相对路径
- 参数示例不是最终真实传参格式
- Header 鉴权被省略

### 8.2 正向能过，异常全错

常见原因：

- 业务码断言写死过于宽松
- 提取值污染环境
- 用例名称和实际场景不一致
- 文档示例是旧版本接口

### 8.3 列表页上下文串了

历史里多次修过“模块切换时仍带旧筛选条件”的问题。

后续如果再改测试用例列表页，要重点防止：

- 模块跳转把旧接口名称筛选带过去
- 项目切换后模块未刷新
- 执行入口没有继承正确上下文

## 9. 建议的后续增强

如果继续加强 API 自动化这条线，优先顺序建议是：

1. ShowDoc 文本解析稳定化
2. 正向用例生成质量稳定化
3. 批量异常场景模板化
4. 用例批量重命名和清洗工具
5. 执行后自动推荐补哪些异常场景

## 10. 一句话原则

这个平台里的接口自动化，不是“只把文档转成 JSON”，而是“把文档转成一个能在目标项目和目标环境里真实执行、可复用、可追踪的测试资产”。
