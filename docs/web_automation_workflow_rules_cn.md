# Web 自动化测试工作流规则

这份文档定义本平台 Web 自动化测试从需求接收、资产录入、执行调试到回归沉淀的默认流程。

核心目标不是临时跑通一次脚本，而是把页面流程沉淀为可执行、可维护、可追踪的测试资产。

## 1. 适用场景

适用于以下类型的需求：

- 指定一个页面、功能或完整业务流程进行 Web 自动化测试
- 为已有项目新增或维护 Playwright 脚本
- 为页面补充或修复元素定位器
- 执行冒烟、回归或失败用例重跑

当前平台默认技术栈为：`Python + Playwright + pytest`。

## 2. 必要输入

开始前优先收集以下信息：

- 所属项目
- 测试目标与覆盖流程
- 页面地址或相对路径
- 运行环境与账号登录方式
- 测试数据及其准备方式
- 每个关键步骤的预期结果或业务断言

如果存在登录态、验证码、权限、跨系统跳转或依赖前置数据，也需要明确处理方式。

## 3. 默认执行流程

### 强制默认前置：用户登录

除登录功能本身、公开页面或用户明确说明无需登录的场景外，后续新增的所有 Web 自动化用例和场景都必须先执行用户登录，再进入目标页面和业务步骤。

- 默认直接复用平台中已启用的用户登录前置脚本；业务脚本不再复制或重新生成登录步骤。
- 登录前置脚本内部继续使用项目定位器库中已验证的登录 XPath。
- 登录账号和密码从运行环境变量 `UI_AUTOMATION_LOGIN_USERNAME`、`UI_AUTOMATION_LOGIN_PASSWORD` 读取，不写死在脚本中。
- 登录前置脚本必须包含明确的成功校验，例如离开登录页、目标页面可见或登录态元素出现。
- 只有明确标记“无需登录”时才能关闭此前置步骤。

### 阶段 1：确认范围并准备测试数据

1. 明确本次只覆盖一条主流程，还是包含异常、权限或边界场景。
2. 确认项目、目标环境、页面地址和浏览器要求。
3. 确认登录账号、用户角色、测试数据来源及清理要求。
4. 将不可自动化的外部依赖（例如验证码、短信、第三方支付）提前标记，并约定模拟、跳过或人工介入方案。

默认先跑通主流程，再按需要补充分支或异常流程。

### 阶段 2：配置或复用运行环境

在平台的 Web 自动化环境中创建或复用以下配置：

- 基础地址（Base URL）
- 浏览器：`chromium`、`firefox` 或 `webkit`
- 无头模式、超时时间和重试次数
- 平台默认的 300 秒运行保护按“连续无新步骤”计算：脚本持续产生实时步骤时会继续执行；连续 300 秒没有步骤进展才会终止。运行参数或环境变量显式指定的运行超时仍作为整次任务的绝对上限。
- 浏览器视口宽高
- 运行变量、代理配置和存储登录态

环境必须归属于目标项目，并保持启用状态。账号、密码、Token 等敏感数据应通过运行变量或受控登录态提供，不硬编码在脚本中。

### 阶段 3：元素定位与定位器录入

这是 Web 自动化的强制约束：

1. 先查询目标项目中已启用的定位器，能复用则不重复创建。
2. 新增定位器时，统一使用 **XPath** 类型。
3. 新 XPath 必须先在真实页面验证：
   - 唯一命中目标元素；
   - 元素在目标步骤可见；
   - 元素在需要交互时可点击、可输入或可选择。
4. XPath 应采用相对路径，优先组合稳定属性、稳定文本或明确的上下文关系。
5. 禁止录入以下不稳定写法：
   - 从 `html/body` 开始的绝对层级 XPath；
   - 依赖页面布局序号的无语义 `div[n]` 链；
   - 随机 class、动态 ID、时间戳或不稳定索引；
   - 在多个元素之间无法唯一命中的 XPath。
6. 验证通过后，将定位器名称、编码、XPath、页面名称、页面 URL 规则、使用场景和稳定性状态录入平台。

定位器编码在同一项目下必须唯一。页面改版或运行失败后，应优先复核并修复已有 XPath，而不是直接堆叠新的重复定位器。

定位器的“页面功能”用于资产归类，必须填写稳定、可复用的业务页面名称，例如“素材工单”“素材库”“登录页”。定位器页会按当前项目汇总这些页面功能；点击“素材工单”后只显示关联到该功能的定位器，也可继续按名称、编码或定位值搜索。切换页面功能或修改搜索条件会清空表格勾选并回到第一页，避免批量操作误处理被筛选隐藏的定位器。在某个页面功能下新建定位器时，表单会默认带入当前功能名称。

### 阶段 4：创建并保存自动化脚本

脚本通过手工创建或批量导入录入平台。每个脚本至少需要录入：

- 所属项目
- 脚本名称和唯一编码
- 入口文件
- 标签、用途说明和启用状态
- 完整的 Playwright 脚本内容

脚本编写规则：

1. 使用 `Python + Playwright` 同步 API 和 `pytest`。
2. 一条脚本尽量只覆盖一条清晰的业务主流程。
3. 优先引用平台中已录入、已验证的 XPath 定位器。
4. 默认先执行用户登录；登录流程应封装为函数、fixture 或 Page Object，避免每条脚本重复实现。只有明确无需登录的场景才允许跳过。
5. 使用 Playwright 的等待能力和 `expect` 断言，不用大量固定 `sleep`。
6. 断言至少覆盖关键页面状态、关键文案、数据变化、跳转结果或业务结果之一，不能只判断页面未报错。

保存或修改脚本后，平台会保留脚本版本；每次修改应有清晰的变更说明。

### 阶段 5：首次执行与调试

选择目标脚本、运行环境和浏览器后，将任务加入执行队列。首次运行重点检查：

1. 是否正确进入目标环境和页面。
2. 登录态、权限和测试数据是否满足前置条件。
3. 每个 XPath 是否在实际步骤中稳定命中。
4. 等待条件是否覆盖异步加载、弹窗、接口返回和页面跳转。
5. 关键断言是否真实校验到业务结果。

平台需保存本次执行的状态、步骤、耗时、日志、截图、Trace 等产物，便于后续回放和定位问题。

执行期间采用真实步骤增量落库：Playwright 步骤开始时记录为 `running`，结束时原记录更新为 `passed` 或 `failed`；按执行批次和步骤序号去重。详情抽屉仅在任务活动状态下按秒刷新，任务结束、页面隐藏或抽屉关闭后停止刷新，结束时再执行一次最终校准。

执行详情必须优先把 Playwright 定位异常细分并展示到对应失败步骤：

- `queued`、`pending`、`running` 属于执行中的非终态，不显示失败分析或异常提示。
- XPath 在限定时间内未命中元素时，显示“元素定位不到”，并展示失败步骤、定位器、原因和处理建议。
- XPath 同时命中多个元素并触发严格模式异常时，显示“元素不唯一”，并尽量展示实际命中数量。
- 只有不满足上述定位异常特征时，才继续归类为断言失败、执行超时或其他脚本异常。
- 原始错误日志继续保留在执行产物中，结构化失败分析用于详情页快速判断问题。

### 阶段 6：失败分析与修复

失败时，按以下顺序排查：

1. 失败步骤、当前 URL、截图和 Trace。
2. XPath 是否唯一、页面是否加载完成、元素是否可见或被遮挡。
3. 登录状态、权限、环境配置和测试数据是否失效。
4. 等待条件、断言逻辑和页面异步行为是否匹配。
5. 页面结构或业务规则是否发生变化。

修复完成后必须生成新的脚本版本并重新执行验证；不能仅因脚本保存成功就视为测试通过。

### 阶段 7：回归沉淀

脚本跑通后：

1. 保留通过的执行记录、步骤截图和相关产物。
2. 将经过验证的 XPath 标记为稳定，失效定位器标记为待观察或废弃。
3. 保留脚本版本和变更说明，避免无法追溯修复来源。
4. 对高频主流程添加清晰标签，作为后续冒烟或回归执行对象。
5. 对需要前置数据、人工操作或外部依赖的流程，在脚本说明中明确限制条件。

## 4. 平台录入清单

每次完整接入至少会在平台中沉淀以下数据：

| 分类 | 录入内容 |
| --- | --- |
| 运行环境 | Base URL、浏览器、超时、重试、视口、运行变量、代理、登录态 |
| 定位器 | XPath、名称、编码、页面、使用场景、稳定性、状态 |
| 自动化脚本 | 项目、名称、编码、入口文件、标签、说明、脚本内容、版本 |
| 执行记录 | 脚本、环境、浏览器、状态、耗时、错误信息 |
| 执行产物 | 步骤明细、截图、日志、Trace、失败分析与回放信息 |

## 5. 一句话原则

执行详情抽屉中的步骤产物采用固定表头与独立滚动区域，步骤列表可以滚动到最后一条，底部不会被抽屉边界或其他内容遮挡。新脚本的步骤名称默认使用中文，定位器编码和 XPath 仍保留技术标识，便于排查。异步页面的控件操作应先等待页面稳定，再滚动到可视区并确认唯一、可见、可用；导航优先等待 networkidle，关键断言使用 20–30 秒超时，提交后等待成功提示和抽屉关闭；下拉选择使用当前可见选项，失败时允许有限次数重试并重新定位，且每次版本更新必须保留已有辅助函数，避免只替换局部函数导致 NameError。

Web 自动化不是“录一段能点击页面的代码”，而是“基于已验证 XPath，将业务流程、脚本、环境和执行证据一起沉淀为可稳定回归的测试资产”。
