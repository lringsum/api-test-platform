## 2. 当前设计的核心方向是对的

从历史会话里的设计建议看，当前实现已经基本沿着正确路线在走：

- 登录态：session
- 授权模型：RBAC
- 数据隔离：project_id
- 审计：AuditLog

所以大方向不建议推翻。

## 3. 目标设计原则

后续权限系统应坚持这四条：

### 3.1 先认证，再授权，再做对象级校验

顺序应当是：

1. 用户是否已登录
2. 用户是否有权限码
3. 用户是否有该项目访问权
4. 用户是否能操作这个具体对象

只做前两层是不够的。

### 3.2 作用域以项目为主

这个平台天然是项目隔离型系统。

所以判断逻辑应该是：

- 用户先拿到“能访问哪些项目”
- 再拿到“在这些项目里能做什么”

不要把它做成纯全局平铺式权限，否则很多资源边界会混乱。

### 3.3 菜单权限只是体验层，不是安全边界

按钮隐藏、菜单不显示只能改善体验，不能替代后端校验。

真正边界必须在：

- 路由
- service
- 对象加载

### 3.4 环境和变量要按高风险资源处理

在这个平台里，高风险资源不是“用户资料”，而是：

- 环境
- 变量
- 用例
- 场景
- UI 自动化脚本

因为它们会直接影响真实执行链路。

## 4. 推荐的权限分层

### 4.1 系统级权限

建议继续保留系统级权限：

- 用户管理
- 角色管理
- 项目成员管理
- 审计查看

这类权限通常只给管理员和少数负责人。

### 4.2 项目级权限

项目级权限是主战场。

建议覆盖：

- 项目查看 / 编辑
- 模块查看 / 编辑
- 环境查看 / 编辑
- 变量查看 / 编辑
- 用例查看 / 创建 / 编辑 / 删除 / 执行
- 场景查看 / 创建 / 编辑 / 删除 / 执行
- 执行记录查看
- 报告查看
- UI 自动化脚本查看 / 创建 / 编辑 / 删除 / 执行
- 定位器查看 / 管理

### 4.3 操作型权限与菜单型权限分开

当前权限码里已经有 `menu / action / admin` 分类倾向，这个方向应继续保留。

原因：

- 菜单决定“看得到什么”
- action 决定“能做什么”
- admin 决定“能管谁”

## 5. 推荐角色模型

当前默认角色基本可用，建议这样理解：

### 5.1 `admin`

- 全局超管
- 拥有全部权限
- 能管理用户、角色、项目成员、审计

### 5.2 `manager`

- 测试负责人 / 项目负责人
- 能配置测试资产
- 能执行和查看完整结果
- 能管理项目成员

### 5.3 `member`

- 普通测试人员
- 能日常设计和执行
- 但不应拥有系统管理权限

### 5.4 `viewer`

- 只读
- 能看项目、报告、执行
- 不能修改核心配置

后续如果有更细角色，优先从现角色拆分，而不是重新发明体系。

## 6. 当前仍然缺什么

尽管骨架已经有了，但从“可上线权限系统”的标准看，仍然可能缺这些补齐项：

### 6.1 路由覆盖不完整

并不是所有业务路由都一定已经加上了 `require_login / require_permission`。

需要系统性补查：

- `app/routes/*.py`

重点查是否存在：

- 页面能进但不该进
- JSON 接口没拦
- 执行入口没拦

### 6.2 service 层对象级授权未必补齐

这是最大风险点。

即使路由层拦住了权限码，如果 service 层拿对象时没有校验：

- 该对象是否属于当前项目
- 当前用户是否能操作该项目对象

还是可能有 IDOR 风险。

尤其要重点检查：

- testcase
- scenario
- environment
- variable
- ui automation script

### 6.3 菜单与权限同步程度可能不够

后台页面如果已经有权限体系，模板层最好也同步做菜单和按钮裁剪。

重点入口：

- `base.html`
- 管理后台导航
- 各列表页的新增 / 编辑 / 删除 / 执行按钮

### 6.4 审计粒度还可以继续细化

目前已有 `AuditLog` 是好事，但建议后续明确记录：

- 谁
- 在哪个项目
- 对什么资源
- 做了什么动作
- 关键变更摘要

优先记录：

- 登录 / 登出
- 成员变更
- 用例创建 / 修改 / 删除
- 环境和变量变更
- 触发执行

## 7. 推荐实施顺序

如果继续做权限增强，推荐顺序是：

1. 先补路由权限覆盖盘点
2. 再补 service 层对象级校验
3. 再补模板层菜单和按钮裁剪
4. 再补审计字段和关键动作记录
5. 最后补更细的角色差异化

这个顺序比“先做复杂角色模型”更稳。

## 8. 具体检查清单

后续动手前，建议用这份清单逐项核：

- 用户未登录时，核心页面是否还能直接访问
- 没有权限码时，核心操作是否仍可 POST 成功
- 没有项目成员关系时，是否还能切换到该项目
- 换一个对象 ID 后，是否还能越权查看或编辑
- 执行类接口是否校验当前项目访问级别
- 管理类入口是否只对管理角色可见

## 9. 一句话结论

这套权限系统最合理的继续路线不是“重新设计”，而是：

在现有 `session + RBAC + 项目成员 + 审计` 的骨架上，把路由覆盖、对象级授权和模板裁剪补完整。
